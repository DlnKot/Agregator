Описание архитектуры 

1. Назначение документа
Документ дает целостное архитектурное описание решения Alfa Remote Client для команд архитектуры, ИБ, эксплуатации и продукта, чтобы у всех было единое понимание:
- зачем клиент нужен в корпоративной среде;
- какую бизнес-ценность он создает;
- как работает сквозной процесс между клиентом, сервером и базой данных;
- как организованы доставка обновлений и сбор телеметрии в сегментированной сети (WAN / DMZ / PVLAN) при управлении доступом через CyberArk.


2. Зачем нужен этот клиент (бизнес-обоснование)
Alfa Remote Client - это единая корпоративная точка входа для запуска и управления удаленными подключениями (RDP, VMware Horizon, Citrix Workspace).

Без такого клиента организация обычно сталкивается с проблемами:
- фрагментированные способы доступа (разные инструменты запуска и ручные настройки по каждой технологии);
- высокая нагрузка на поддержку (ошибки пользователей в настройках broker/pool/endpoint и параметров запуска);
- неоднородный пользовательский опыт между подразделениями и ОС;
- низкая наблюдаемость реального использования и причин инцидентов;
- медленный и слабо контролируемый цикл доставки обновлений.

Клиент закрывает эти проблемы за счет:
- единой управляемой точки входа в удаленный доступ;
- централизованных дефолтов и policy-driven развертывания;
- стандартизированного UX и процесса онбординга;
- контролируемого канала обновлений по HTTPS;
- телеметрического контура для операционных и продуктовых метрик.


3. Границы решения и ключевые участники
3.1 В периметре
- Десктопный клиент, используемый конечными пользователями в WAN.
- API-сервер обновлений и метрик, размещенный в DMZ.
- Хранилище телеметрии в БД сегмента PVLAN.
- Защищенный доступ к привилегированным учетным данным и сессиям через CyberArk.

3.2 Участники
- Конечный пользователь: запускает удаленные сессии и работает с функциями клиента.
- Клиентское приложение: хранит локальные настройки, проверяет обновления, отправляет метрики.
- Сервер обновлений/метрик (DMZ): отдает метаданные/пакеты обновлений и принимает метрики.
- Artifactory: источник утвержденных бинарных артефактов для обновлений.
- База данных (PVLAN): хранит телеметрию и операционные записи для анализа/аудита.
- Команды ИБ/платформы: управляют политиками CyberArk, сертификатами и правилами доступа.


4. Логическая архитектура
4.1 Клиентский слой (WAN)
- Десктопное приложение на Electron с локальным хранилищем.
- Управление подключениями, профилями и настройками технологий удаленного доступа.
- Проверка обновлений по HTTPS.
- Сбор сессионных метрик использования и локальная буферизация при необходимости.

4.2 Серверный слой (DMZ)
- Публикация HTTPS endpoints для:
  - проверки манифеста/версии обновления;
  - выдачи пакета обновления (или подписанного redirect/stream);
  - приема метрик.
- Валидация запросов клиентов и контроль транспортной безопасности.
- Чтение утвержденных артефактов из Artifactory.
- Запись принятых метрик в БД PVLAN по контролируемому каналу.

4.3 Слой данных (PVLAN)
- Выделенные таблицы телеметрии для сессий/событий/агрегатов.
- Доступ только с DMZ-сервера через разрешенный сетевой путь и секреты CyberArk.
- Прямой путь WAN-клиент -> БД отсутствует.

4.4 Контур управления безопасностью (CyberArk)
- Предоставляет защищенные креденшелы/секреты для доступа сервера к Artifactory и БД.
- Обеспечивает ротацию учетных данных и аудит обращений.
- Снижает риск хранения статических секретов в конфигурациях клиента и сервера.


5. Сетевая сегментация и модель доверия
5.1 Сегменты
- Клиентский сегмент: WAN (сеть конечных пользователей).
- Сервисный сегмент: DMZ (пограничный сервисный контур).
- Сегмент данных: PVLAN (ограниченный сетевой сегмент для БД).

5.2 Разрешенные потоки
- WAN Client -> DMZ Server: только HTTPS (обновления, API метрик).
- DMZ Server -> Artifactory: только HTTPS (получение артефактов/метаданных).
- DMZ Server -> PVLAN DB: протокол БД по разрешенному маршруту, креденшелы через CyberArk.
- DMZ Server -> CyberArk: защищенное получение секретов/управление сессиями.

5.3 Запрещенные потоки
- Прямой доступ WAN Client -> PVLAN DB.
- Прямая production-зависимость WAN Client -> Artifactory (кроме явно утвержденных исключений).
- Хардкод привилегированных учетных данных в клиентском приложении.


6. Функциональный процесс A: управление обновлениями (клиент запрашивает обновление)
Цель: доставлять клиентам только утвержденные обновления из Artifactory через контролируемый DMZ API.

Пошагово:
1) Инициация
- Клиент запускает проверку обновлений (по расписанию или вручную).

2) Запрос
- Клиент отправляет HTTPS-запрос на endpoint обновления в DMZ с текущей версией/платформой/каналом.

3) Решение на сервере
- DMZ-сервер валидирует метаданные клиента и применимую политику.
- DMZ-сервер проверяет наличие утвержденного артефакта в Artifactory.
- Если доступна подходящая более новая версия, сервер возвращает описание обновления (версия, release notes, URL пакета, подпись/хэш).
- Если обновления нет, сервер возвращает статус "актуальная версия".

4) Доставка
- Клиент загружает пакет обновления по разрешенному HTTPS-пути.
- Клиент проверяет целостность/подпись пакета.

5) Применение
- Клиент устанавливает обновление по локальной политике (сразу или при перезапуске/закрытии приложения).

6) Аудит и наблюдаемость
- DMZ-сервер логирует решение и метаданные выдачи.
- Опционально в метриках фиксируется результат проверки и установки обновления.

Ключевой архитектурный принцип:
- Управление артефактами выполняется в Artifactory.
- Клиент получает обновление через контракт DMZ-сервиса, а не через прямые неконтролируемые каналы.


7. Функциональный процесс B: жизненный цикл метрик (раз в неделю или при закрытии клиента)
Цель: собирать операционную/продуктовую телеметрию с контролируемой передачей и надежным хранением.

Модель сбора:
- Клиент открывает сессию метрик при старте приложения.
- В течение сессии накапливаются события и агрегаты (использование, запуски, просмотры вкладок, проверки сети, ошибки и т.д.).

Условия отправки:
- Условие 1: периодическая пакетная отправка (например, 1 раз в неделю).
- Условие 2: отправка при закрытии клиента (graceful flush при завершении приложения).

Пошагово:
1) Локальная агрегация
- Клиент накапливает метрики в локальном буфере.

2) Отправка по триггеру
- По недельному расписанию или при закрытии клиента формируется payload и отправляется по HTTPS на endpoint метрик в DMZ.

3) Прием на сервере
- DMZ валидирует схему payload, метаданные источника и транспортное доверие.
- DMZ записывает принятые данные в БД PVLAN, используя учетные данные, полученные через CyberArk.

4) Контур надежности
- При недоступности DMZ/таймаутах клиент сохраняет payload в локальной очереди pending.
- Невыгруженные данные повторно отправляются в следующее разрешенное окно.

5) Хранение и аналитическая готовность
- БД хранит записи сессий/событий с таймстампами и идентификаторами клиента (по умолчанию без ПДн, если иное не утверждено отдельно).
- Данные используются для отчетности, операционных дашбордов и улучшения продукта.


8. Бизнес-процесс (сквозной: клиент, сервер, БД)
Название процесса: Управляемый удаленный доступ и операционная наблюдаемость.

8.1 Основной поток
1) Пользователь открывает клиент и запускает утвержденное удаленное подключение.
2) Клиент обеспечивает консистентность конфигурации и фиксирует события использования.
3) Клиент периодически проверяет доступность обновлений через DMZ-сервис.
4) DMZ-сервер определяет применимость обновления на основе артефактов Artifactory.
5) Клиент обновляется до актуальной утвержденной версии, снижая поддержку и security-drift.
6) Клиент отправляет метрики раз в неделю или при закрытии.
7) DMZ сохраняет метрики в БД PVLAN через доступ, управляемый CyberArk.
8) Команды архитектуры/поддержки используют аналитику, чтобы:
   - выявлять проблемы адаптации и использования;
   - корректировать дефолты и политики;
   - повышать надежность и качество пользовательского опыта.

8.2 Бизнес-результаты
- Снижение числа инцидентов из-за некорректных настроек удаленного доступа.
- Более быстрый и контролируемый rollout обновлений безопасности и функциональности.
- Измеримые показатели использования и качества для принятия управленческих решений.
- Повышение аудируемости за счет сегментированной сетевой модели и контроля привилегированного доступа.


9. Домены данных и минимальный контракт
9.1 Домен обновлений (DMZ)
- Вход: clientVersion, platform, channel.
- Выход: признак updateAvailable, targetVersion, метаданные артефакта, release notes, атрибуты целостности.

9.2 Домен метрик (DMZ -> PVLAN DB)
- Заголовок сессии: sessionId, clientId, appVersion, sessionStart/sessionEnd, duration.
- События: тип события, timestamp, контекстные атрибуты.
- Агрегаты: запуски по типам, счетчики вкладок, счетчики проверок сети, сводка ошибок.

9.3 Принципы данных
- Приоритет операционной телеметрии без персональных данных.
- Хранение только необходимых полей для поддержки и продуктовой аналитики.
- Политики retention/purge согласуются с ИБ и legal.


10. Контроли безопасности и соответствия
- TLS обязателен для всех коммуникаций клиент/сервер и сервер/внутренние сервисы.
- Серверные сертификаты управляются корпоративным PKI, клиент доверяет утвержденной цепочке CA.
- CyberArk используется для хранения/ротации привилегированных секретов (доступ к БД и Artifactory).
- Строгие ACL между WAN/DMZ/PVLAN по модели deny-by-default.
- Структурированное логирование и трассируемость решений по обновлениям и приему метрик.
- Валидация входных данных и контроль схемы на endpoint метрик.
- Отсутствует прямой клиентский доступ к привилегированным backend-компонентам (БД, контур секретов).


11. Операционная модель
- Развертывание: десктопный клиент распространяется на корпоративные рабочие станции.
- Обновления: контролируемое продвижение релиза в Artifactory, затем доступность через DMZ API.
- Мониторинг: здоровье DMZ API, успешность проверки/доставки обновлений, успешность приема метрик.
- Обработка отказов:
  - недоступен endpoint обновлений -> клиент остается на текущей версии и повторяет попытку позже;
  - недоступен endpoint метрик -> локальная буферизация и отложенная повторная отправка.


12. Риски и меры снижения
- Риск: целостность цепочки поставки обновлений.
  Мера: подпись артефактов, проверка хэшей, контролируемое продвижение в Artifactory.

- Риск: потеря метрик при сбоях.
  Мера: устойчивая клиентская очередь + политика повторных отправок.

- Риск: компрометация учетных данных.
  Мера: получение секретов через CyberArk во время выполнения, без хардкода production-секретов.

- Риск: lateral movement между сегментами.
  Мера: изоляция зон (WAN/DMZ/PVLAN), минимизация east-west разрешений.


13. Высокоуровневая последовательность (текстом)
Обновления:
Client (WAN) -> DMZ Update API (HTTPS) -> Artifactory (HTTPS check/fetch) -> ответ DMZ -> загрузка/установка на клиенте.

Метрики:
Client (WAN) --(раз в неделю или при закрытии, HTTPS)--> DMZ Metrics API --(креденшелы CyberArk + подключение к БД)--> запись в PVLAN DB.


14. Резюме архитектурного решения
Выбранная модель разделяет пользовательский доступ, сервисный контур и хранение данных по выделенным зонам доверия (WAN, DMZ, PVLAN), а CyberArk управляет привилегированным доступом между слоями. Это обеспечивает контролируемую доставку обновлений из Artifactory и надежный сбор телеметрии в рамках корпоративных требований по безопасности, наблюдаемости и соответствию.
